# A Content Credential is read, and exactly one part of it is checked

**Status: living.**

augur reads C2PA Content Credentials wherever a file can carry one, reports what they
say, and verifies **one** thing about them: the hard binding, which is the claim's hash
over the file's own bytes. Everything else in a credential is reported as a quotation —
what the file says about itself — and nothing in augur implies it was checked.

## Why the binding is the part worth verifying

Every other question a credential raises needs something augur does not have. Is the
signer real? That is a certificate trust list. Was the timestamp honest? That is a
timestamp authority's chain. Is the generator's name true? Nobody can tell from the file.

The binding is different: the claim carries a hash over the asset with the manifest's own
bytes excluded, and recomputing it needs the file and nothing else. No key, no network,
no trust list. Either the bytes still hash to what was signed, or **the file is not the
file that was signed** — and that is a fact augur can establish on its own and stand
behind.

It is also the fact people actually want. A credential that says "generated by a model"
on a file that has since been edited is describing something else.

## What is deliberately not done

- **The signature is not verified and the certificate chain is not validated.** Reading
  the certificate's subject and printing it is not the same as checking it, and a report
  that blurs those is worse than one that omits the second. The blind-spots panel says
  so in the same words.
- **Nothing is fetched.** A file may point at a manifest kept elsewhere — a URL in a
  comment, an HTML link element. augur reports the pointer and does not follow it. A file
  inspector that makes network requests while inspecting an untrusted file has given away
  more than it gained.
- **Box hashes, BMFF hashes and collection hashes are not recomputed.** Each would mean
  reproducing a container's own box map — a second implementation of the walkers, and a
  second chance to be subtly wrong. They are named as unchecked rather than ignored.

## The precondition that keeps a mismatch honest

A mismatch is an accusation: it says a file was changed after it was signed. So the check
refuses to run unless the claim's exclusion ranges contain the manifest's own bytes,
which every real producer's do — a manifest cannot hash itself. When they do not, augur
is not looking at the layout the claim was written against, and it reports the binding as
unchecked with the reason rather than hashing anyway and reporting a difference.

That rule is not hypothetical. It is what keeps augur quiet about a real file in the C2PA
reference corpus (`no_alg.jpg`) whose exclusions miss 197 bytes of the manifest, and it
is what the exclusion-coverage test pins.

## What this means for cleaning

A credential is metadata in a box, and it is removable like any other metadata: a JPEG
segment, a PNG chunk, a WebP chunk, an element in an SVG, a run of characters in text.
Removing anything **else** from a signed file breaks its binding, and the next scan says
so — which is correct, and worth knowing before deciding to strip an EXIF block from a
file whose provenance you wanted to keep.

In a PDF or an Office document nothing is removable at all, for the reason in
[lossless-only](lossless-only.md): those are read and never written.
